# Billy Constitution

## Core Principles

### I. Enforced Module Boundaries
The Nx workspace MUST respect the scope-tag dependency graph: `api`/`worker` → shared, db, ai;
`web` → shared only; `ai`/`db` → shared; `shared` → shared. Code in `apps/web` MUST NOT import
`packages/db` or `packages/ai`. Any new tag or rule MUST be added to `eslint.config.mjs` and is
enforced by `@nx/enforce-module-boundaries`.
Rationale: keeps server-only logic and secrets out of the browser bundle and the architecture
mechanically checkable.

### II. Workspace Packages via Nx
Internal libraries MUST be named `@org/<name>`, consumed as workspace packages
(`"main": "./src/index.ts"`) and wired with `pnpm add @org/<name> --workspace --filter <consumer>`;
tsconfig `paths` MUST NOT be used. Project configuration MUST live in each `package.json` under
the `nx` key (no `project.json`). All tasks MUST run through Nx (`pnpm nx <target> <project>`)
and the package manager MUST be `pnpm` (never npm or yarn).
Rationale: one consistent, cacheable task graph and dependency model.

### III. Environment-Driven Configuration
Configuration MUST come from environment variables, with `.env.example` as the source of truth.
`.env` is local and MUST NOT be committed. Compose passes container-internal hosts; `.env` uses
`localhost` for apps run on the host. Secrets MUST NOT appear in source or images.
Rationale: identical code runs locally, in containers and in deployment.

### IV. Local-Stack Parity and S3 Compatibility
The local stack (Postgres with pgvector, Redis, SeaweedFS S3, api, worker, web) MUST be runnable
via the documented `pnpm` scripts. Docker images MUST be Nx targets (`docker:build`) tagged
`apps-<name>`, and compose MUST use `pull_policy: never`. Storage code MUST use only
S3-compatible SDK features. `infra/README.md` MUST be updated in the same change whenever
compose, scripts or ports change.
Rationale: reproducible development and no dependency on provider-specific behavior.

### V. Verified Changes (NON-NEGOTIABLE)
Every change MUST pass format, lint, test, typecheck and build on affected projects before it is
committed or merged. New behavior MUST be covered by tests proportionate to its risk, and
shared schemas and contracts in `packages/shared` MUST have tests. Failing checks MUST be
reported, never hidden.
Rationale: a monorepo with shared packages can break distant consumers silently.

## Technology Constraints

- Stack: NestJS 11 (api on port 3000, global prefix `/api`; worker as an application context
  with BullMQ consumers), Next.js 16 App Router with React 19, HeroUI v3 and Tailwind 4,
  Postgres with pgvector, Redis, SeaweedFS (S3 API only).
- Shared types and validation live in `packages/shared` as zod schemas; LLM logic lives in
  `packages/ai`; database access lives in `packages/db`.
- Files under `.agents/`, `.cursor/`, `.github/skills`, `.opencode/`, `.codex/` and `.gemini/`
  are generated by Nx and MUST NOT be hand-edited.

## Development Workflow

- Commits MUST follow Conventional Commits in English (e.g. `feat(infra): ...`); Prettier uses
  single quotes.
- Changes touching architecture or tags SHOULD be reviewed with `billy-boundary-reviewer`;
  changes touching Docker, compose, env or scripts SHOULD be reviewed with
  `billy-infra-reviewer`.
- Run `billy-verify` (the quality gate) before committing or opening a PR.
- New libraries MUST follow `billy-add-lib`; new containerized services MUST follow
  `billy-dockerize-app`.

## Governance

This constitution supersedes other practices. Amendments MUST be made through a documented
change to this file, include a Sync Impact Report, and update dependent docs (`CLAUDE.md`,
`infra/README.md`) in the same change. Versioning follows semantic versioning: MAJOR for
backward-incompatible removals or redefinitions of principles, MINOR for added or materially
expanded principles or sections, PATCH for clarifications and wording. All PRs and reviews MUST
verify compliance, and any deviation MUST be justified in the PR description. Use `CLAUDE.md`
for runtime development guidance.
